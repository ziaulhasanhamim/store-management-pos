# Inventory and receiving

- `/items`: paginated catalog, search by name/barcode/ID. Signed-in store roles can browse; sales associates receive no cost data.
- `/items/new`, `/items/{id}/edit`: inventory-role item editing with enhanced SSR forms. New items start with zero stock and cost; receiving establishes cost.
- `/items/{id}`: stock totals and a location selector for the latest 100 stock movements at that location. Locations are ordered by name and the first is selected by default; `?locationId=` supports direct links. Archived locations remain selectable when the product has history there. The selector is a small Interactive Auto component; product details and filtered history remain streamed SSR. Historical purchase lines retain item name/barcode/unit snapshots after catalog edits.
- `/receiving`: streamed SSR shell with an Interactive Auto receipt editor for search and receipt editing, Blazor quick-add dialogs, supplier/location creation, and partial/full payment. An empty database can be set up from this page. New suppliers can have an opening due or advance.

InventoryService owns short-lived DI scopes and EF contexts for every operation. It rechecks roles in the database, including writes from an existing interactive circuit. Entity models remain property-only.

API handlers live in `Endpoints`, with static route handlers and `RouteGroupBuilder` mapping extensions for items, suppliers, stock locations, and receiving. Shared form inputs, DTOs, requests, and responses live in `POSApp.Client/DTOs`; shared enums live in `POSApp.Client/Enums`. User management continues to use enhanced SSR forms.

Products have `AllowFractionUnit`, defaulting to false in both C# and the database. Whole-unit products reject fractional receipt quantities; enabled products support up to three decimal places. This rule is enforced by the receipt editor and InventoryService. Fractional units cannot be disabled while fractional stock remains. Apply the `AddProductAllowFractionUnit` migration before running against an existing database.

Receiving uses `DecimalField` text inputs with decimal keyboards and no number steppers. The first click or keyboard focus selects the full value; typing replaces that selection. Invalid text remains visible and blocks submission. `number-fields.js` handles the focus selection without triggering server requests.

Receiving commits purchase/lines, stock balances, movements, average cost, supplier balance, invoice history and payment history in one serializable EF transaction. The cost is weighted by the product's existing stock across all locations because CostPrice belongs to the product. Example: `(1 × 100 + 1 × 200) / 2 = 150`. Average cost is rounded to two decimals, quantities support three, and line totals round to two before summing.

The full purchase total increases CurrentBalance and creates an invoice entry with its BalanceAfter snapshot. Any payment creates SupplierPayment plus a negative balance entry with a second snapshot. Existing opening balances and dues remain intact when a purchase is fully paid.

A stable receipt request GUID generates its unique purchase reference. Retrying the same request returns the previously saved receipt rather than adding stock twice. Concurrent serializable conflicts return a retry message; submitting again retains that GUID. New receipt creates a new GUID. In-progress receipts currently live in the Interactive Auto component and are not persisted as drafts across browser reloads. Saving keeps the confirmation visible; the SSR receipt history can be refreshed from its link.

Tailwind is rebuilt with `npm run css:build`. Run `dotnet run --project POSApp.Persistence.Tests` for weighted averages across locations, opening/partial/full dues, movement history, retry protection, input validation, authorization/cost privacy, immutable purchase snapshots, and SSR item form/streaming checks. Tests use disposable SQLite; production uses PostgreSQL. Set `POS_TEST_PREVIEW=1` to run a disposable browser preview with sample catalog data after the checks pass.

Quick-add modals are rendered from C# component state. Blazor event handlers manage close, cancel, backdrop click and Escape. Focus uses `ElementReference.FocusAsync`, and focus sentinels keep keyboard navigation inside the modal. The receiving editor behind the modal is inert, and dismissing is blocked while a save is pending. No custom dialog-opening JavaScript is loaded.

# Returns, barcodes, suppliers and sales

Receiving accepts negative quantities for supplier returns and positive quantities for purchases in the same receipt. Sales can take a location's stock below zero when a sale is made before the goods are entered; later receipts replenish that negative balance. Supplier returns still require enough stock at their location. Purchases that replenish non-positive aggregate stock set the average cost to the received unit cost; otherwise they use the moving weighted average. Supplier returns preserve the product's existing average cost and are applied before new purchases when calculating the updated average. A net return credits the supplier balance; cash refunds are not entered as negative payments.

The product form preserves a manually entered barcode. With “Generate barcode when empty” selected, saving obtains the database-generated ID and assigns its seven-digit padded value plus the EAN-8 check digit: ID 1 is `00000017`, ID 44 is `00000444`. The Items page supports selecting multiple products and printing names, SVG barcode bars and readable codes at `/items/labels`. Missing codes are generated without replacing existing codes. Manual printable ASCII barcodes use Code 128; valid eight-digit codes use EAN-8. Copies per product are configurable. Print layouts hide the dashboard navigation.

`/suppliers` lists stored opening/current balances, `/suppliers/{id}` shows the account history, and `/suppliers/payments` records payments against opening or accumulated due. Payments and negative ledger entries commit together. Stable request IDs and unique references prevent duplicate postings on retries. Overpayment becomes an advance.

`/sales` streams an SSR shell and supplies initial data to the Client project's Interactive Auto `SalesEditor`. Search by name/barcode or enable hardware scanner mode for keyboard scanners that finish with Enter. Camera scanning uses the browser's BarcodeDetector API on HTTPS/localhost when available; unsupported browsers show a message and retain keyboard/manual entry. Camera tracks stop on close, scan, navigation and disposal. Customer dialogs are controlled by C#.

Sales support a selected stock location, customer, quantities, prices, discount, partial/due/full payments and cash change. Due sales require a customer. Drafts are persisted per cashier with planned payment, without reserving stock or posting financial entries. Completing a draft revalidates availability, deducts stock, creates movements, posts the customer invoice and actual payment, and commits everything in one serializable transaction. Cash received above the total is change, rather than an inflated payment or account credit. Checkout retries reuse the same request ID. `/sales/{id}/bill` shows immutable line snapshots and a printable receipt; configure `Store:Address` and `Store:Phone` for bill contact details.

`/reports` links sales, receiving/returns and supplier payment history. Transaction reports provide today, yesterday, last seven days, this month, last month and inclusive custom dates with pagination. Date boundaries and displayed times use `BusinessTimeZone` (default `Asia/Dhaka`); the database stores UTC. Sales associates see their own completed sales, while inventory managers/admins can see all sales. Drafts are excluded.

Apply the `AddSalesDraftPaymentsAndPaymentReferences` migration with `dotnet ef database update --project POSApp` before running these features against an existing database. This adds planned draft payment, cash tendered and unique payment references. The implementation does not update your existing database automatically. `CommerceChecks` covers mixed returns, average cost, barcode examples, supplier payment retries, draft isolation, partial payments, cash change, stock validation and report date boundaries. HTTP checks also cover antiforgery, static SSR label forms and report/supplier/sales page rendering.

## Roll labels, split tenders and line profit

Barcode labels print one label per page using a named CSS page size with zero margins. The default is 57.15 × 25.4 mm (2.25 × 1 inch); presets also include 50 × 30, 50 × 25, 40 × 30 and 60 × 40 mm. Choose the physical stock in both the label screen and the printer driver, use 100% scaling, and disable browser headers/footers. EAN-8 symbols retain a fixed physical width instead of filling the entire label. A label printer's media calibration and driver settings still control the physical feed/gap.

Sales now use a search/scan box above the added-item table, with customer, subtotal, discount, net total and confirmed payments on the right. Fast scanner bursts are captured and queued locally, clearing the field for the next scan before the server lookup finishes. An exact barcode match also automatically adds the item after normal input settles, without requiring Enter. Name searches show selectable results. Enter remains an optional shortcut. Added sales and receiving rows show nonempty barcodes.

The shared `SplitPayments` client component confirms one method/amount at a time. Only confirmed rows are included on the order; the remainder is due. Confirmations are local until checkout/receiving commits. The server validates the ordered payment list again: non-cash tenders cannot exceed the outstanding amount; a final sales cash tender may include change. It posts only the applied amount and stores the tendered cash separately. Every actual payment has its own ledger entry. Draft payment rows are stored separately from actual payments so saving/resuming a draft never changes an account balance.

The UI shows only the whole-order discount; bill item amounts remain gross. Internally, order discounts are allocated by each line's gross extended price (`quantity × unit price`), rather than equally by units or product count. For gross lines of 100 and 300 with a discount of 40, the saved discounts are 10 and 30. Whole cents are allocated first; leftover cents go to the largest fractional remainders, tied by line order. Zero-price items receive no allocation. `SaleItem.UnitPrice` remains the gross selling price. `UnitDiscount` stores the allocated line discount divided by quantity, with 20 decimal places available for repeating values. The database generates `TotalAmount` as `(UnitPrice - UnitDiscount) * Quantity` at currency precision. `Sale.DiscountAmount` is saved from the sum of `UnitDiscount * Quantity` across all items, rounded once to currency precision. Therefore line gross profit is `TotalAmount - Quantity × UnitCost`, using the checkout cost snapshot. Do not subtract the order discount a second time. The migration also allocates discounts on historical gross sale lines so earlier sales follow the same representation.

Apply `AddSplitPayments` before running this version. It adds persisted draft payment rows and per-payment tendered amounts; existing single-payment API requests and draft rows remain readable. Tests cover split payments and account snapshots, updated drafts, cash change, price-weighted allocation, cent reconciliation, historical backfill and item profit.

Run `node --test POSApp.Client.Tests/barcode-scanner.test.mjs` for keyboard scanner boundary detection, queued lookups, optional Enter suffix, ordinary typing and disposal. The scanner's local capture is the only additional JavaScript behavior; dialogs and payment confirmation remain in Blazor/C#.


Apply `AddSaleItemUnitDiscount` for the per-unit representation and generated line total column. The migration renames and converts existing line discounts using their quantities. It preserves totals when rolling back as well. Per-unit allocations remain internal: the checkout and printed bill show a single discount for the order.

## Default suppliers, returns, and administrator corrections

A product requires an active default supplier selected in the regular form or receiving quick-add dialog. The default supplier is independent of any particular receipt’s actual supplier. Items show this association and, for inventory roles, stock value. Supplier pages compare stored due against the current cost value of all stock assigned to that supplier. This is an association-based view, not lot provenance.

`/reports/inventory` values all locations or a selected location using current product average cost. Filters include default supplier and name/barcode. Totals cover the full filtered result rather than the current page. Archived products with stock remain included so archiving cannot hide inventory value. Cost information requires an inventory role.

The sales editor has a return mode that adds negative quantities. Sales and returns of the same product can coexist. Enter the original net selling price for a return; automatic original-invoice matching is not implemented. Order discounts apply only to positive sale lines. Net refunds accept negative split payment amounts, and any unpaid refund becomes a customer credit. Walk-in transactions must settle in full. Drafts retain return quantities and refund methods without changing stock or balances.

Administrators can open a correction page from sale bills, receiving details, or product details. Transaction date/time uses the business timezone and is saved in UTC; the original creation timestamp remains unchanged. Changing a supplier/customer transfers the net outstanding amount through account adjustment entries. Actual payment time and the original ledger snapshots remain retained. A reason and matching record revision are required, and every change stores before/after snapshots in `RecordChanges`.

Deleting a sale or receiving is a soft delete in one serializable transaction. It appends inverse stock movements named `Sale delete #ID` or `Purchase delete #ID`, reverses the net account due, and excludes the transaction from active reports/drafts. Original items, payments and ledger entries remain available in the database. Repeated deletion is harmless. Deleting a product archives it without changing stock. Inventory staff and sales staff cannot perform these administrator operations.

After transaction deletion, product cost is replayed from remaining inventory movements in posting order, ignoring deleted transactions and reversal entries. Purchases/opening stock/positive adjustments establish weighted average; sales and returns consume or restore quantities at the current average. Effective date corrections do not reorder historical costing. For one unit at 100 followed by one at 200, deleting the second receipt leaves one unit at cost 100. Deletions that would produce negative current or intermediate stock fail and roll back all changes. Existing sale cost snapshots remain unchanged.

Apply `AddDefaultSuppliersAndRecordCorrections` with `dotnet ef database update --project POSApp`. It adds supplier foreign keys, soft-delete fields and the administrator audit table. Existing products use their latest active purchase supplier; those without supplier history are assigned a clearly named legacy supplier for later review. Fresh product forms require an explicit selection. No migration is applied automatically by this change.

`AdministrationChecks` covers returns/exchanges, partial split refunds, supplier valuation, administrator-only corrections, stale revisions, stock and due reversals, preserved records, atomic rollback, and weighted average after deletion. HTTP checks submit the enhanced correction/deletion forms and verify timezone conversion and retained history.

## Purchases, transfers and location receiving reports

`/receiving` contains a Purchase / Stock transfer selector; `/stock/transfers` redirects to its transfer mode. The page is streamed SSR with separate Interactive Auto editor islands in the client project. Transfer mode searches by product name, barcode or ID, shows source-location availability, and accepts multiple items without supplier, invoice, cost-entry or payment fields. A single serializable operation validates all lines, updates both locations, and records paired movements; retries share a unique request ID.

Transfers stay separate from purchases in persistence: `StockTransfer` owns source, destination, date, notes and `StockTransferItem` lines. Each line saves quantity and average unit cost at posting time. Transfers do not alter global average cost, supplier/customer balances, cash, or purchase totals. `MultiItemStockTransfers` moves existing single-product transfer fields into item rows and copies original movement cost, preserving transfer IDs and movement links. Its downgrade cannot safely represent multi-item documents and is intentionally unsupported.

`/reports/receiving` combines purchases, supplier returns and transfers for the selected dates and location. All locations includes a positive destination row and a negative source row for each transfer, so the net stock value is zero. A single location shows only its side. Ten units transferred at a saved average cost of 1,500 show +10 / +15,000 at the destination and −10 / −15,000 at the source; later receiving costs do not change those values. Purchase payments remain separate from transfer stock value. Net received value is movement during the period, not ending inventory value.

### Stock additions without purchases

Admins can use **Items → Stock adjustments** (`/stock/adjustments`) to add stock without a supplier invoice or any payment. The page uses the receiving layout: search by name, barcode or ID; add products to an editable quantity/cost list; choose the location, date and notes in the summary panel; then **Add stock**. Existing products remain available even after trading begins. Quantities are increments, not replacement counts. **New item** opens a Blazor dialog using the same product fields as receiving and adds the created product to the manual list.

`StockAdjustment` and `StockAdjustmentItem` store the batch and product/cost snapshots. A serializable transaction adds the signed quantity to the selected location, updates weighted average product cost for positive additions, and records linked `InventoryMovementType.Adjustment` movements plus an audit record. Zero-quantity rows are retained in the batch history without changing stock or cost. Negative adjustments can make stock negative. Adjustments create no purchase, payment, supplier/customer balance entry, cash/bank movement or trading profit. Non-stocked products, invalid quantities/costs, disallowed fractional units, duplicate rows and closed accounting periods are rejected. Stock take remains the workflow for comparing physical counts with expected quantities and recording shortages/extras.

Product JSON imports accept an optional positive `id`. A supplied ID becomes the product's database ID and must be unused; an omitted or null ID is generated by the database. The importer synchronizes the PostgreSQL identity sequence after explicit IDs so later database-generated IDs do not collide. Stock adjustment JSON takes an array of objects containing `productId`, `quantity` and `unitCost`. All fields are required. Quantity may be positive, zero or negative; zero records a no-change row, while a negative value reduces stock and may leave it below zero. Product IDs must already exist. Up to 1,000 products / 2 MB are accepted. Selecting the file posts the entire batch immediately after validation; it does not populate the manual item list or clear its pending entries. One invalid row prevents the whole batch from being added. The example download uses productId 0 intentionally: replace it with a real product ID before importing. Reselecting the same data with the same admin, location, date and notes produces the same request ID, so uncertain-response retries do not add stock twice. The editor shows only an import result and a history summary; item details are available separately if opened.

Unposted manual entries are recovered from browser storage for the signed-in user. Legacy opening-inventory drafts, URLs and database records are preserved during the transition. New records use the stock-adjustment model and movement type; historical opening movements retain their original type.

### Owner funding and account statements

Owner contributions and withdrawals use explicit cash movement kinds. They change cash/bank balances and net assets, without creating sales, expenses, payroll, or profit. Day and month finance show owner funding separately and persist it in closed snapshots; monthly assets also show asset change excluding net owner funding. Generic historical cash-in/payout records remain generic because their original purpose cannot be inferred from a note. Bank corrections remain signed balance adjustments; bank deposits/withdrawals remain paired drawer transfers.

Admins can use **Reports → Cash drawer statements / Bank & digital statements** for a day, month, year or custom range. The cash drawer and bank pages also show their selected working day's step-by-step movements. A statement follows business dates and shows posted times, receipts, payouts, reversals, count shortages/overages and a running balance. Initial funds on the starting day are included in opening balance exactly once. Cash counts bridge expected cash to actual closing cash; reopening a drawer removes that count adjustment until it is closed again. Internal transfers appear on both affected accounts. Reversals remain visible for audit history; their gross money-in/out differs from a finance summary that suppresses corrected pairs, while net balance reconciles.

Running balances and totals include every movement, not just the current page. Statements use 50 rows per page and calculate the brought-forward amount before the page. One database snapshot covers the balances and rows so concurrent transactions cannot mix different states. Year-to-date profit and loss is available through the standard report year preset and excludes owner funding.
